# Field test — 2026-08-20 sunset, three devices

**Scene:** Prague river, afternoon → night, ~18:07–19:13 UTC.
**Arms:** iPad Air M1 (BLEND Auto / Latitude, EVERY 3s, Holy Grail armed) ·
iPhone 16 Pro (BLEND Auto / Lumen, EVERY 3s, Holy Grail armed) ·
iPhone 12 Pro (BLEND fixed 5, EVERY 5s — settings unchanged from an earlier
test; Holy Grail NOT armed).

Regenerate this audit any time:

```
tools/.venv/bin/python tools/blend_compare.py report <A>/source/capture_log.json <B>/... <C>/... --labels a,b,c --csv shoot.csv --plot shoot.png
tools/.venv/bin/python tools/shoot_audit.py <A> <B> <C> --labels a,b,c --out audit-YYYY-MM-DD
```

## Verdict

The **12 Pro — the un-configured control — produced the only usable record**
of the transition (EV walked 6.7 stops, late-run rendered luma 0.299, 0%
shadow clip). Both Holy Grail arms delivered **black frames**: the iPad from
~t+20 min (749 frames all at ISO 80 · 1/60s, EV span 0.0000), the 16 Pro from
~t+44 min (a two-state AE dither, span 0.29 stops). This was **not a strategy
failure and not a ramp failure**.

## Root cause (verified against code and the shoot's own sidecars)

The Holy Grail engine worked perfectly — `frames.timestamps` shows it
commanding a full sunset ramp on both devices (iPad: 0.085s/ISO 18 →
1.0s/ISO 59, model EV 8.02 → 2.75; 16 Pro: → 1.0s/ISO 191), correlating with
the 12 Pro's real AE at **r = 0.97**. The commands never reached the sensor:

- The DNG path captures via **bracketed RAW** (default ON), and
  `fireBracket` builds `AVCaptureAutoExposureBracketedStillImageSettings.
  autoExposureSettings(exposureTargetBias:)` — per-shot exposure specs that
  **override the device's custom exposure** set by
  `applyHolyGrailExposure`'s `setExposureModeCustom`.
- With the device in `.custom` mode the AE loop stops converging, so the
  "auto" brackets resolved to the **pre-lock AE state** (iPad: 1/60 · ISO 80,
  all 2,247 captures) while the world fell ~5.3 stops.
- Contributing: commanded values ran **out of device gamut** (ISO 18 below
  minISO; shutter pegged at the 1.0 s cap), consistent with rejected custom
  writes on the iPad.
- The 12 Pro ran the **same capture code** without Holy Grail: its AE loop
  stayed live, the same auto brackets tracked it, and it rode the sunset
  down. That contrast is the proof.
- **Nothing compares commanded vs delivered**, so a 6-stop divergence was
  silent for 51 minutes. (Free detector found in the data: healthy DNGs held
  17–19 MB; the starved ones compressed to 9.5 MB.)

## What each subsystem actually did

- **Zone / Latitude** never differentiated — their input (`sceneEV`, the
  device's commanded exposure) froze with the actuation, so counts sat at
  3 (iPad) and 2 (16 Pro base). The strategy comparison is a wash **because
  the input was severed**, not because the strategies are equivalent.
- **Lumen was the only subsystem that saw the sunset.** Its pixel score
  tracked the real light (including a genuine 18:25–18:40 re-brightening all
  three devices witnessed), crossing 0.5 within 2 minutes of the 12 Pro's
  AE dive, peaking 0.92/0.94. Its +2 boost actuated on the 16 Pro (2→4
  frames) — correctly powerless to brighten a mean blend, but the *signal*
  is exactly a ramp-health watchdog.
- **EVERY=Auto re-pacing worked, bidirectionally** (3→5s, back to 3s through
  the re-brightening, then →8s), driven by the engine model.
- **12 Pro's dropped frames:** processing-bound from window 1 (median 5.3 s
  of processing per 5 s window; +147.6 s cumulative drift). Its 53 short
  windows are mostly 25 **burst-splits** across window boundaries (pairs
  summing to 5) — cadence stutter in the clip, not bad frames. Thermal went
  `serious` at t+2.7 min and stayed (704/736 windows) but did not cluster
  the failures; the fixed-5×5s ask was simply beyond it. BLEND Auto's probe
  + ceiling exists for exactly this.

## Actions

1. **Actuation fix — DONE (same day):** under Holy Grail, brackets are built
   with `AVCaptureManualExposureBracketedStillImageSettings.
   manualExposureSettings(exposureDuration: AVCaptureDevice.
   currentExposureDuration, iso: AVCaptureDevice.currentISO)` — the
   `current` constants resolve on the device at capture time, so the bracket
   carries the ramp's custom exposure and is range-proof against format
   switches during teardown (explicit clamped values were not — an
   out-of-range manual bracket raises an uncatchable exception).
   `applyHolyGrailExposure` additionally clamps commanded ISO/shutter to the
   `activeFormat` envelope before writing (the field test commanded ISO 18,
   below the iPad's floor), stores the applied value for the guard, and
   arming warns if the camera cannot do custom exposure at all. Plain
   (non-ramped) runs keep auto-exposure brackets — a live AE is exactly what
   those should follow.
2. **Commanded-vs-delivered honesty guard — DONE (same day):** every RAW
   frame's EXIF ISO/shutter is compared against the ramp's applied target;
   >0.5 stop divergence logs loudly (rate-limited, re-arming on recovery)
   and stamps `exposureDivergenceStops` into the window's `capture_log.json`
   record, which `blend_compare.py` reports as a RAMP ACTUATION FAULT. The
   ramp's own 1/3-stop step plus ISP latch stays under the threshold by
   construction. This bug dies on frame 1 next time. (Guard covers the DNG
   path; the video path's continuous frames follow device exposure
   directly.)
3. **Lumen v2 = ramp watchdog:** starving-score high while commanded EV is
   static ⇒ alarm/act. The blend-count boost stays; the signal gains a
   second, more valuable job.
4. **12 Pro protocol:** BLEND Auto next time (ceiling right-sizes it), or
   fixed depth with EVERY ≥ 7 s.
5. Re-run the same three-device protocol after the fix; audit with the two
   tools above and compare against this report.
